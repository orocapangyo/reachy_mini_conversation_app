## 아키텍처

### 핵심 결정 1 — 리스너는 마이크를 직접 열지 않는다 (feed 방식)

마이크는 이미 콘솔 오디오 입력 경로가 소유하고 있다. 웨이크 리스너가 장치를 또 열면
플랫폼별 장치 경합이 생기므로, **기존 입력 경로가 프레임을 밀어넣는(feed) 수동 구조**로
한다. 장치 관리 코드 0줄, 단위 테스트는 wav 프레임 주입으로 끝난다.

```
기존 오디오 입력 ──frame──▶ WakeWordListener.feed(sample_rate, pcm)   [논블로킹 enqueue]
                               │ 내부 워커 스레드: 16kHz mono 정규화 → 엔진
                               ▼
                         WakeWordEngine.process(...) → 감지 시 on_wake() 콜백
```

**삽입 지점 (글루 PR 몫, 인터페이스 합의)**: `console.py`의 `record_loop`
(약 :1123-1139)는 `get_sample → noise_gate → handler.receive` 파이프라인이다.
여기의 **noise gate 판정 이전**에 `listener.feed(input_sample_rate,
audio_to_int16(audio_frame))` 한 줄을 추가한다 — 수면 중 게이트/뮤트 상태와
무관하게 웨이크 워드는 들려야 하므로 raw 프레임 기준. (별도 오디오 탭/스트림을
만들지 않는다 — 기존 루프가 feed를 추가 호출하는 해석이 유일하게 옳다.)
수면 중에도 `record_loop`는 `_stop_event` 기준으로 계속 돌므로 프레임 공급은
유지된다 (핸들러 세션 종료와 무관).

**스레딩 경계**: `record_loop`는 이벤트 루프에서 돈다. 엔진 추론(~30ms+)이
루프를 막으면 안 되므로 `feed()`는 **논블로킹 enqueue만** 한다 (고정 크기 큐,
가득 차면 가장 오래된 프레임 드롭). 추론은 리스너 소유의 **단일 워커 스레드**에서
수행하고, `on_wake` 콜백은 `loop.call_soon_threadsafe`로 이벤트 루프에 전달한다.

### 핵심 결정 2 — 엔진은 프로토콜 뒤로 격리

```python
class WakeWordEngine(Protocol):
    def process(self, pcm_16k_mono: NDArray[np.int16]) -> str | None:
        """감지된 웨이크 문구를 반환, 없으면 None. 내부 상태(스트리밍) 유지."""
    def reset(self) -> None: ...
    def close(self) -> None: ...   # tflite 인터프리터 등 자원 해제
```

**리스너 수명 주기 (명세)**: `start()`/`stop()`은 멱등 (중복 호출 no-op).
`stop()` 후 `feed()`는 조용히 드롭. 감지 직후 **쿨다운 3초** (상수
`WAKE_COOLDOWN_S = 3.0`) 동안 재감지 억제 — `stop()`이 쿨다운도 초기화.
감지 시 INFO 로그: 문구·신뢰도 점수·타임스탬프 (오탐/미탐 디버깅용).

- 구현 1: `<스파이크 결과 엔진>Engine` — §엔진 선정 참조
- 구현 2: `MockWakeEngine` — 주입된 스크립트대로 반응 (테스트·시뮬·Windows 폴백)
- 엔진 의존성 임포트는 **지연 임포트** — 미설치 환경에서 앱이 죽지 않고
  mock/비활성으로 폴백 (`{"error": ...}` 철학과 동일)

### 핵심 결정 3 — 수면 라우터의 셋째 경로

`main.py`의 `go_to_sleep_action()`은 이미 standby/앱종료 분기 라우터다:

```
현행:  standby 지원 핸들러 + 플래그 → request_standby()   (OpenAI)
       아니면                       → 수면 모션 + 앱 종료
추가:  핸들러 standby 불가 + 웨이크 모듈 활성
       → "로컬 standby": 수면 모션 + (핸들러 세션 종료) + WakeWordListener 활성
         감지 시: 리스너 중지 → 기상 모션 → 세션 재기동 → 인사
```

단, **라우터 수정 자체는 후속 글루 PR 몫** — 이 PR은 리스너 모듈과 mock,
설정만 제공한다 (인터페이스 합의용으로 본 설계에 명시).

### 문구 매칭 재사용

### 설정 (`config.py` + `.env.example`)

**의미 구분 (critic 지적 반영)** — 두 개념을 섞지 않는다:
- `REACHY_MINI_WAKE_PHRASES`: **STT 전사 매칭 전용** (OpenAI standby 경로). 자유
  텍스트로 변경 가능. 음향 엔진에는 **아무 효과 없음** — 기존 의미 그대로 유지.
- 음향 엔진의 감지 문구는 **학습 시점에 고정**("reachy mini")이며 설정으로 바꿀 수
  없다. 문구를 바꾸려면 재학습이 필요하다는 사실을 `.env.example` 주석에 명시.

신규 변수:
- `REACHY_MINI_WAKE_WORD_ENABLED` (기본 0 — opt-in)
- `REACHY_MINI_WAKE_ENGINE` (`openwakeword` | `mock`, 기본 `openwakeword`)
- `REACHY_MINI_WAKE_MODEL_PATH` (기본: 리포 내장 모델 — 아래 배치 참조)

구현 주의: config.py는 Config 클래스 본문과 `refresh_runtime_config_from_env()`
**양쪽**에 변수를 추가해야 한다 (기존 코드에 클래스 본문 내 중복 대입 버그 패턴이
있으니 그걸 복제하지 말 것 — 각 1회씩, 총 2곳).

## 엔진 선정 — 기술 선택 기록 (ADR)

### 왜 "전용 웨이크 엔진"이 자명한 답이 아닌가

웨이크 워드 감지의 정석은 전용 엔진(특정 소리 패턴만 감지, 초경량)이다. 그러나
**한국어 커스텀 문구 "리치미니"** 라는 요구가 정석을 흔든다:

| 기준 | 전용 엔진 (openWakeWord / Porcupine) | 소형 STT + 문구 매칭 (Vosk-ko) |
| :--- | :--- | :--- |
| 설계 적합성 | 본래 용도 — 최적 | 범용 STT를 웨이크에 쓰는 **과한 도구** |
| 자원(CPU/메모리) | 가벼움 | 더 무거움 — **실측 필수** (로봇은 소형 컴퓨터) |
| 한국어 커스텀 문구 | openWakeWord: 영어 위주, 커스텀 **학습 파이프라인 필요** / Porcupine: 상용 라이선스·AccessKey (오픈소스 공모전 적합성 의심) | 한국어 모델만 있으면 **어떤 문구든 즉시**, 문구 변경 = 설정 1줄 |
| 기존 코드 재사용 | 불가 | OpenAI standby의 `matches_wake_phrase` 그대로 |
| 오프라인/비용 | 로컬 | 로컬 (모델 82MB 1회 다운로드) |

**판단 원칙**: "이상적 도구가 막혀 있을 때, 차선이 충분히 싼지를 숫자로 확인한다."
→ 스파이크(`scripts/wake_word_spike.py`)로 Vosk small의 감지율·오탐·실시간 배속·
메모리를 실측하고, 통과하면 Vosk 채택 / CPU 과다면 openWakeWord 커스텀 학습
비용을 재평가한다.

### 관점 전환 (2026-10-27, 사용자 인사이트)

> **"리치미니를 꼭 한글로 인식해야 할까? 원래 영어잖아."**

웨이크 엔진이 듣는 건 음향 패턴이지 표기가 아니다 — "한국어 커스텀 문구"라는
프레임 자체가 불필요한 제약이었다. 이로써 선택지가 재편된다:
- openWakeWord: "reachy mini"를 **영어 문구로 학습**하면 공식 파이프라인(영어 TTS
  합성) 그대로 사용 가능 — 1차의 "한국어라 감점" 평가 철회. 단 한국식 발음
  (또박또박 4음절) vs 영어 강세 리듬의 억양 차이 리스크 → 학습 데이터에 한국어
  TTS 샘플 혼합으로 완화
- Vosk **영어** 소형 모델: 한국식 "리치미니" 발음이 "richie mini"류로 일관 전사되는지
  2차 스파이크에서 실측
- 보조 문구 "일어나/깨어나"는 순수 한국어 → v1 범위를 "리치미니" 단일 문구로
  좁히는 선택지 포함

- 방어 개선: standby 진입 시 `robot.disable_wobbling()`(레거시 수면 경로와 동일),
  기상 시 `enable_wobbling()` → 데몬 死 시 에러 폭주 억제 + 수면 중 머리 흔듦 방지.
- **미해결**: 안정적 데몬 1회 확보 후 웨이크 감지→기상 전체 체인 재검증 필요.

### 글루 데드락 수정 (2026-10-30)

재테스트(데몬 정상·1012 없음)에서 **수면 직후 이벤트 루프 전체가 멎는** 증상 —
로그가 "Tool cancelled: go_to_sleep"에서 동결, 마이크·모션 전부 먹통. 원인은
**순환 대기(deadlock)**:
- go_to_sleep 툴(툴 스레드) → `request_local_standby().result()`에서 블록
- `enter_local_standby`(루프) → `await self._receive_task`에서 블록
- receive 태스크 정리(`_run_live_session` finally) → `tool_manager.shutdown()`이
  go_to_sleep 툴 완료 대기 → go_to_sleep은 standby를 기다림 → **순환**

OpenAI standby는 세션을 안 닫아(전사 모드 전환) 이 문제가 없었음. Gemini는
go_to_sleep 안에서 세션을 닫다가 자기 꼬리를 뭄.

수정: ⑴ `request_local_standby`를 **fire-and-forget**(`.result()` 블록 제거) →
go_to_sleep 툴 즉시 반환. ⑵ `enter_local_standby`가 receive 태스크를 **await 없이
취소만** → 순환 고리 제거. 게이트 537 통과. **실기 재검증 대기.**

### 스테레오 프레임 드롭 수정 (2026-10-30)

데드락 수정 후: 수면 중 "리치미니" 무반응 + 진단 로그상 **엔진 점수 0개
(0 chunks processed)**. 원인: 앱 마이크 프레임이 **스테레오 2D**인데, 버퍼링
워커의 `np.concatenate([buffer(1D), pcm(2D)])`가 매 프레임 예외 → 전량 드롭 →
엔진에 오디오 0 도달. (이전 "Invalid input shape {2}" 에러의 진짜 정체.)
수정: 워커가 버퍼 적재 전 `_to_mono_1d()`로 (N,C)/(C,N)→모노 1D 평탄화.
진단 로그(청크 수·peak score)도 추가. 게이트 537. **실기 재검증 대기.**

### 시작 세그폴트 완화 — 엔진 지연 로드 (2026-10-30)

웨이크 동작 성공 후 관찰: 앱이 시작 직후(첫 오디오 재생 무렵) **간헐적
세그폴트**(`zsh: segmentation fault`)로 종료 — 3회 재현. 네이티브(C레벨) 크래시로,
시작 시 여러 네이티브 라이브러리(GStreamer 오디오 + onnxruntime 웨이크 모델 +
MuJoCo 카메라)가 동시 초기화되며 발생하는 레이스로 추정. 우리 onnxruntime 로드가
그 초기화 폭풍에 한몫.
완화: `WakeWordListener`가 엔진 인스턴스 대신 **팩토리**를 받아 **첫 start()(=첫
수면) 때 지연 로드** → onnxruntime이 앱 시작 초기화에서 빠짐. 로봇이 첫 수면 전엔
웨이크 불필요하므로 기능 손실 없음. 근본(환경 네이티브 취약성)은 아니나 시작
경합을 줄여 세그폴트 빈도 감소 기대. 게이트 537. **실기 재검증 대기.**
